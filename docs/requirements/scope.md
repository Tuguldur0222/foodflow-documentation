# FoodFlow — SRS Scope Charter

**UE-2 · Шинэчилсэн:** 2026-10-13 · **Төлөв:** хянан батлуулах ноорог.

## Зорилго ба уншигч

FoodFlow-ийн шаардлагын тодорхойлолт (Software Requirements Specification, **SRS**) нь хоол сонгохоос захиалгын дараах хяналт хүртэлх хэрэглэгчийн урсгалыг тодорхойлно. Уншигч нь product owner, frontend/backend хөгжүүлэгч, QA, support баг; анхдагч persona нь [Ану](../audience/personas.md).

## Хамрах хүрээ

**Хамруулна:** Хоолны жагсаалт, хайлт, дэлгэрэнгүй; сагсанд нэмэх, тоо өөрчлөх, устгах, нийт дүн; хүргэлтийн хаяг, боломжит цаг, төлбөрийн арга, захиалга үүсгэх; өөрийн захиалгын төлөв, түүх, зөвшөөрсөн төлөвийн цуцлалт, амжилтын баталгаа. Эдгээр нь сонголт, зардал, нэг захиалгын бүрэн мэдээлэл, дараах хяналтад хэрэгтэй. MUST/SHOULD/COULD эрэмбийг [SRS](srs.md) тогтооно.

**Хасна:**

- Рестораны бүрэн admin CMS — хэрэглэгчийн захиалгын хүрээнээс тусдаа ажилтны бүтээгдэхүүн.
- Courier route optimization — хүргэлтийн зам оновчлох нь тусдаа ажиллагааны систем.
- Картын нууц мэдээлэл хадгалах — загварт энэ үүргийг payment provider-т хариуцуулсан.

**Хойшлуулна:** Урамшуулал, loyalty, promo campaign-ийг үндсэн урсгалын дараа; live courier map, автомат refund, төлөвийн push мэдэгдлийг бизнесийн дүрэм ба гаднах интеграц батлагдсаны дараа хэлэлцэнэ. Эдгээрийг эхний хувилбарт хэрэгжсэн гэж амлахгүй.

## Хил ба баталгаажуулах зүйл

Загвар нь веб интерфейс, HTTPS/JSON API, гадаад төлбөр болон мэдэгдлийн үйлчилгээтэй; үнэ төгрөгөөр илэрхийлэгдэнэ. Provider-ийн бодит холболт, production ажиллагаа баталгаажаагүй. Рестораны төлөв шинэчлэх үүрэг нь гаднах оролцогчийн хил; бүрэн staff UI энэ хүрээнд орохгүй.

W01–W04 нь бүтээгдэхүүний суурь шаардлага, [архитектурыг](../architecture/index.md) тодорхойлно. W05 OpenAPI ба локал mock нь сонгосон HTTP гэрээг үзүүлнэ. W06 Python модуль нь захиалга үүсгэх, өөрийн захиалга унших, Pending захиалга цуцлах жишээ; бүтэн веб бүтээгдэхүүний баталгаа биш. SRS-ийн Pending/Confirmed цуцлалттай зөрөх хэсгийг [мөрдөх хүснэгтэд](traceability.md) хэрэгжүүлэлтийн дутагдал гэж бүртгэнэ.

**“Just enough” шийдвэр:** Нэг захиалгын урсгалыг шалгаж болох хэмжээнд бичиж, шаардлага, интерфейс, тестийг холбоно. Шалгах боломжгүй дэд системийн дэлгэрэнгүйг баталгаажсан мэт нэмэхгүй. Бодит захиалагчийн зөвшөөрөл хүлээгдэж байна.

**Өөрчлөх дүрэм:** Шинэ семинарын pull request-д шалтгаан, нөлөөлөх шаардлага, API/архитектур, тест, эзэн, шийдвэрийн төлөвийг хамт шинэчилнэ. ID-ийн өмнөх утга ба өөрчлөлтийн түүхийг хадгална.
