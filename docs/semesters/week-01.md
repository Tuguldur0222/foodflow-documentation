## 1. Баримтжуулалтын дөрвөн төрөл

**Getting Started — эхлэх заавар.** “Эхний үр дүнгээ харахын тулд юу суулгаж, юу ажиллуулах вэ?” гэсэн асуултад хариулна. Ихэвчлэн `README`, `intro/install/`, `first-steps/` зэрэг эхлэх цэгт байрлаж, урьдчилсан нөхцөл, хамгийн богино үйлдэл, хүлээгдэх үр дүнг өгнө.

**Tutorial — дараалсан сургалтын заавар.** “Тодорхой ажлыг эхнээс нь дуустал яаж хийх вэ?” гэсэн асуултад алхам бүрээр хариулна. Ихэвчлэн `tutorial/`, `intro/tutorial01/`, `user/quickstart/` хэсэгт байрлаж, нэг алхмын үр дүнг дараагийн алхамд ашиглана.

**Reference — лавлах.** “Энэ нэр, тохиргоо, өгөгдлийн төрөл ямар утгатай вэ?” гэсэн асуултад төвлөрнө. Ихэвчлэн `reference/`, `ref/`, `reference/arrays.html` хэсэгт байрлаж, хэрэгтэй мэдээлэл рүү шууд очих бүтэцтэй байна.

**API Documentation — интерфейсийн лавлах.** “Энэ функц эсвэл endpoint ямар оролт авч, ямар үр дүн, алдаа өгөх вэ?” гэсэн асуултад хариулна. Ихэвчлэн function/class reference, OpenAPI файл эсвэл `/docs` хэлбэрээр байрлаж, параметр, төрөл, гаралт, алдааны гэрээг тайлбарлана.

API documentation нь reference-ийн нэг хэлбэр байж болно. Доорх хүснэгтэд хичээлийн дөрвөн төрөлд нийцүүлэн интерфейсийн дэлгэрэнгүй гэрээг тусад нь ангилсан; нэг хуудас хэд хэдэн үүрэг гүйцэтгэх боломжтой.

## 2. Persona ба түүний хэрэгцээ — US-1.2

Анхдагч persona нь зохиомол Nomad Eats компанийн junior frontend developer **Ану**. Тэр React, TypeScript, VS Code, Chrome DevTools, Postman, GitHub ашиглан захиалгын интерфейсийг API-тай холбох бөгөөд auth, алдааны гэрээ, хувилбарын нөхцөл нь тодорхой байхыг хүснэ.

Бодит олон нийтийн эх сурвалжтай гурван асуудал, persona-ийн дэлгэрэнгүй, дэмжих дүрүүд, **end-end user** Саруул болон 30 минутын ярилцлагын төлөвлөгөөг [persona баримтад](../audience/personas.md) нэгтгэсэн. Үүнд `P-ANU-01` — token дамжуулах нөхцөл, `P-ANU-02` — оролт ба гаралтын алдааны ялгаа, `P-ANU-03` — жишээний хувилбарын нийцэл гэсэн тогтвортой ID ашиглав.

Зохиомол persona-ийн хэллэг нь бодит ярилцлагын эшлэл биш. Handout-ийн ярилцлагад тулгуурлах хэсгийг бүрэн хаахын тулд нэргүй оролцогчийн зөвшөөрөл, огноо, тэмдэглэл, илэрсэн асуудал шаардлагатай; одоогоор энэ шалгуур хүлээгдэж байна.

## 3. Curse of Knowledge — README-ийн өөрийн үнэлгээ — US-1.3

**Curse of Knowledge** нь өөрийн мэддэг зүйлийг уншигч мөн мэднэ гэж таамаглах хандлага юм. Доорх “өмнө” өгүүлбэрүүд нь эхний DOCX-д README-ийн ноорог гэж тэмдэглэгдсэн жишээ; одоогийн README-ийн тухайн үеийн commit эсвэл инженер бус хүний шалгалтын протокол хавсаргагдаагүй. Иймээс үүнийг баримтжуулалтын self-audit гэж тэмдэглэв.

| Өмнө — эхийн ноорог | Нуугдсан мэдлэг / асуудал | Дараа — шинэчилсэн найруулга |
| --- | --- | --- |
| “Стандарт stack-аа асаагаад ердийн seed ажиллуул.” | Ямар орчин, тушаал, өгөгдөл, үр дүнг хэлсэн нь тодорхойгүй. Өмнөх засварт бичсэн Docker/seed файл repository-д баталгаажаагүй. | “Жишээ Python модулийн шалгалтыг төслийн үндсэн хавтсаас `python -m unittest discover -s tests -v` тушаалаар ажиллуулна. Орчин бэлтгэх алхмыг README-ээс үзнэ.” |
| “Protected route-уудаас өмнө энгийн bearer flow ашигла.” | Token авах болон хүсэлт бүрд дамжуулах хоёр алхмыг ялгаагүй. | “HTTP API-ийн хамгаалалттай хүсэлтэд access token-оо `Authorization: Bearer <access_token>` header-аар дамжуулна. Нэвтрэлтийн бодит үйлчилгээ болон W06-ийн Python жишээний хэрэглэгчийн ID-г ялгаж ойлгоно.” |
| “Retry хийхэд idempotency автоматаар ажиллана.” | Давтан хүсэлт яагаад аюулгүй болох, key ба payload-ийн дүрэм, баталгааны хил алга. | “Давхар захиалга үүсэхээс сэргийлэхийн тулд захиалга үүсгэх HTTP гэрээнд заасан `Idempotency-Key`-г ашиглана. Давтан хүсэлт, өөрчлөгдсөн өгөгдөл болон хүчинтэй хугацааны дүрмийг API гэрээнээс шалгана.” |

Гурав дахь засварын эхэнд хэрэглэгчид чухал үр дүнг тавьсан нь **Most Important Information First** зарчмын жишээ. Анхны тайлангийн засварт дурдсан “24 цаг” гэсэн хугацааг бодит хэрэгжүүлэлтээр батлаагүй тул нийтлэг баталгаа болгож үлдээгээгүй. Python жишээний key-ийн амьдралын хугацаа болон HTTP гэрээний TTL-ийг адил гэж үзэхгүй.

```diff
- Retry хийхэд idempotency автоматаар ажиллана.
+ Давхар захиалга үүсэхээс сэргийлэхийн тулд API гэрээнд заасан Idempotency-Key-г ашиглана.
+ Давтан хүсэлт болон хүчинтэй хугацааны нөхцөлийг тухайн интерфейсийн гэрээнээс шалгана.
```

**Инженер бус уншигчаар шалгах дараагийн алхам:** Гурван зассан өгүүлбэрийг харуулж “Энэ алхмыг хэзээ хийх вэ?”, “Ямар үр дүн хүлээх вэ?”, “Тодорхойгүй үлдсэн үг юу вэ?” гэж асууна. Огноо, ашигласан commit, нэргүй оролцогчийн ID, өөрийн үгээр тайлбарласан хариу болон дахин зассан diff-ийг хадгална. Эдгээр бодит хариу байхгүй тул “уншигчаар баталгаажсан” гэж дүгнээгүй.

### 3.1 Гурван бодит төслийн нэршилд хийсэн контекстийн шалгалт

Handout-ийн sprint goal-д гурван бодит repository-ийн мэдлэгийн таамгийг танихыг дурдсан тул дээрх FoodFlow-ийн гурван өгүүлбэрээс гадна дараах богино үнэлгээг нэмэв. Эдгээр нь албан эхэд байгаа нэршил; эх хуудсууд тайлбарыг нь мөн өгдөг. Доорх нь тэдгээр хуудсыг доголдолтой гэж тогтоосон хэрэглэгчийн тест биш, шинэ уншигчид тайлбарлахдаа ямар контекстийг эхэнд өгөх тухай редакцийн үнэлгээ юм.

| Төсөл ба эхийн богино хэллэг | Урьдчилан мэднэ гэж үзвэл үүсэх саад | FoodFlow-д хэрэглэх энгийн тайлбарын загвар |
| --- | --- | --- |
| FastAPI: “path operation” — [First Steps](https://fastapi.tiangolo.com/tutorial/first-steps/#step-3-create-a-path-operation) | URL зам болон HTTP method-ийн хослолыг мэдэхгүй хүн function-той андуурч болно. | “`GET /orders/{id}` гэдэг нь захиалгын URL руу GET хүсэлт илгээж мэдээлэл унших үйлдэл.” |

FoodFlow-ийн жишээний баримт Django эсвэл NumPy ашигладаг гэсэн утгагүй. Эндээс авч буй зарчим нь шинэ нэршилд тодорхой утга, жижиг жишээ өгөх; уг жишээний техникийн үнэн зөв байдлыг эхтэй тулгах юм.

## 4. Writer-in-the-Middle — 200 үгийн эргэцүүлэл — US-1.4

FoodFlow багт баримт бичиг бичигчийн үнэ цэнэ нь хүмүүсийн мэдлэгийг нэг ойлголтод холбох явдал юм. Marketing-д давхар захиалгаас сэргийлэх боломжийг хэрэглэгчийн хэлээр тайлбарлана. Product-д захиалга цуцлах боломжтой төлөвийг шаардлага, хүлээн авах нөхцөлтэй нь холбож өгнө. Sales-д төлбөрийн сонголтыг төлөвлөсөн болон хэрэгжсэн байдлаар нь ялган, баталгаагүй амлалтаас сэргийлнэ. Support-д алдааны утга, хэрэглэгчийн хийх дараагийн алхмыг нэг дороос олох заавар бэлтгэнэ. DevRel-д эхний захиалга үүсгэх ажиллах жишээ болон турших нөхцөлийг өгнө. Engineering-д шаардлага, архитектур, интерфейс, тестийн өөрчлөлтийг хооронд нь мөрдөнө. Machine Readers-д OpenAPI schema, тогтвортой талбарын нэр, шалгаж болох өгөгдлийн жишээ хүргэнэ.

Writer-in-the-Middle үүрэг нь баг бүрийн хэлснийг шууд хуулж нэгтгэхээс илүү хариуцлага шаарддаг. Би хөгжүүлэгчээс бодит ажиллагааг, бүтээгдэхүүний эзнээс бизнесийн дүрмийг, support-оос түгээмэл асуултыг тодруулж, зөрүүг ил гаргана. Нэг шийдвэр өөрчлөгдвөл түүнээс хамаарах жишээ, алдаа, тестийг хамт шинэчилнэ.

Ану баримтын шууд уншигч боловч түүний бүтээсэн дэлгэцээр Саруул хоол захиална. Ану төлөвийн дүрмийг буруу ойлговол Саруул цуцлагдаагүй захиалгаа цуцлагдсан гэж бодож болно. Иймээс end-end user-ийн үр дүнг баримтын чанарын шалгуурт оруулна. Ажиллуулаагүй тестийг амжилттай, батлаагүй интеграцыг бэлэн гэж бичихгүй. Тодорхойгүй зүйлд эзэн, дараагийн шалгалт, нотолгооны төлөв оноож, уншигчид итгэж болох баримт үлдээнэ.

Ингэснээр шинэ хөгжүүлэгчийн асуултад хариулах хугацаа багасаж, багийн шийдвэр дараагийн семинар болон дараагийн хувилбарт ойлгомжтой, шалгаж болох хэлбэрээр хадгалагдан үлдэнэ.

Үгийн тоог зайгаар тусгаарласан нэгжээр тоолсон: **200**. Долоон нөлөөллийн хүрээ тус бүрд FoodFlow-ийн жишээ орсон; энэ нь хийгдсэн бизнесийн үр ашгийн хэмжилт бус, баримтжуулалтын үүргийн эргэцүүлэл юм.

## 6. Definition of Done ба нотолгоо

## 7. Эргэцүүлэл ба дараагийн семинарт шилжүүлэх зүйл

**Bhatti-ийн нөлөөлсөн ойлголт:** Handout-д заасан Ch. 1, p. 3 дахь Curse of Knowledge нь “ердийн seed” гэх хэллэгт хэрэгжүүлэх мэдээлэл дутагдаж байгааг илрүүлэхэд тустай. Ch. 3, p. 58 дахь мэдээллийг ач холбогдлоор нь эрэмбэлэх зарчмаар техникийн механизмыг тайлбарлахаас өмнө уншигчийн авах үр дүнг бичив.

**Цааш хэрэглэх хүрээ:** Chinchilla Ch. 2, pp. 9–24-ийн дөрвөн төрөл нь эхлэх заавар, сургалт, лавлах, API гэрээний үүргийг ялган байрлуулахад ашиглагдана. Нэг README-д бүх мэдээллийг давтахын оронд шаардлагын болон интерфейсийн үндсэн эх рүү холбоно.

**Онол ба одоогийн ажлын зөрүү:** Уншигчтай баталгаажуулах ёстой боловч одоогийн багцад бодит ярилцлага, инженер бус уншигчийн туршилт байхгүй. Тиймээс хэрэгцээний таамгийг ил тод тэмдэглэж, дараагийн өөрчлөлтөөр нотолгоо нэмэх боломжтой бүтэц бэлтгэв.

| Standup / retrospective асуулт | Энэ шинэчлэлийн хариу |
| --- | --- |
| Ямар гурван төслийг ангилсан бэ? | FastAPI, Django, NumPy |
| Persona-ийн явц ямар вэ? | Дүр ба эх сурвалж бэлэн; бодит ярилцлага хүлээгдэж байна |
| Ямар jargon-ийг зассан бэ? | Stack/seed, bearer flow, retry/idempotency гэсэн гурван жишээ |
| Юу сайн болсон бэ? | Бодит эх сурвалж, зохиомол дүр, хэрэгжүүлэлтийн нотолгоог ялгасан |
| Юу цаг авсан бэ? | Анхны тайлангийн баталгаажаагүй команд, холбоос, хугацааг тулгах шаардлагатай байсан |
| Дараа юу өөрчлөх вэ? | Persona-ийн асуудлыг W02 шаардлага бүрийн эх сурвалжтай холбож, уншигчийн бодит шалгалтыг бүртгэнэ |

Энэ хүснэгт нь шинэчилсэн ажлын өөрийн үнэлгээ; багийн бодит standup, retrospective уулзалтын тэмдэглэл биш.
