# W02 — SRS-ийн хамрах хүрээ ба мөрдөх холбоо

Энэ семинараар FoodFlow-ийн шаардлагын тодорхойлолтын (Software Requirements Specification, **SRS**) хүрээг тогтоож, IEEE 830-ийн бүтцийг төсөлдөө зураглан, шалгаж болох таван шаардлага болон найман баганатай мөрдөх хүснэгт бэлтгэв. Гол зорилго нь олон хэсэгтэй загвар бөглөх бус, ямар хүний хэрэгцээг ямар шаардлагаар шийдэх, түүнийг юугаар батлахыг тодорхой болгох юм.

| Талбар | Утга |
| --- | --- |
| Суурь материал | `Week_02_FoodFlow.docx`; `Software_Project_Documentation_Week_02_Handout.pdf` — [эх сурвалжийн бүртгэл](../../sources/README.md), [файлын manifest](../../sources/manifest.json) |
| Холбогдох даалгавар | `US-2.1`–`US-2.3`, заавал хийх `UE-2` |
| Шинэчилсэн огноо | 2026-10-13 |
| Өмнөх оролт | [W01](week-01.md), [persona](../audience/personas.md) |
| Дараагийн гаралт | [W03](week-03.md), [SRS](../requirements/srs.md), [нэгдсэн мөрдөх хүснэгт](../requirements/traceability.md) |
| Нотолгооны хязгаар | Шаардлагыг бичиж хянасан; бүтэн FoodFlow бүтээгдэхүүн дээр эдгээр тестийг гүйцэтгэсэн гэж мэдүүлээгүй |

## Семинарын user story-ууд

| ID | Үүрэг → хүсэл → үнэ цэнэ |
| --- | --- |

| `US-2.2` | Оюутны хувьд ID, эрэмбэ, эх сурвалж, эзэн, шалгах аргатай таван шаардлага бичихийг хүсэж байна. Ингэснээр шаардлагыг тесттэй холбож, биелсэн эсэхийг ажиглаж болно. |
| `US-2.3` | Оюутны хувьд шаардлага бүрийг найман баганатай traceability-д бүртгэхийг хүсэж байна. Ингэснээр эх сурвалж, хамаарал, эрсдэл, шалгалтын төлөвийг дараагийн аудитад мөрдөнө. |

## 1. SRS Scope Charter — UE-2

[Нэг хуудсанд зориулсан Scope Charter](../requirements/scope.md) нь энэ семинараар хүлээлгэн өгөх бие даасан баримт юм. Түүнд хамруулах, хасах, хойшлуулах боломжуудыг шалтгаантай нь бичиж, бүтээгдэхүүний өргөн хүрээг W05-ийн HTTP гэрээ болон W06-ийн хязгаарлагдмал Python жишээнээс ялгасан.

### 1.1 Хүрээ тогтоох асуултыг хэрэглэх нь

Доорх асуултуудыг Chinchilla Ch. 5, pp. 53–55 гэсэн handout-ийн чиглэлийг FoodFlow-д хэрэглэхээр өөрийн үгээр найруулсан. Номын асуултыг үгчлэн эшилсэн гэж үзэхгүй.

| Асуулт | FoodFlow-ийн шийдвэр |
| --- | --- |
| Баримтыг хэн, ямар шийдвэр гаргахад ашиглах вэ? | Product owner хүрээг, хөгжүүлэгч зан төлөв ба интерфейсийг, QA pass/fail нөхцөлийг, support хэрэглэгчийн дараагийн алхмыг шалгана. |
| Эхний хувилбарын зайлшгүй үр дүн юу вэ? | Нэг захиалгын сонголт → сагс → checkout → өөрийн захиалгын хяналтыг тодорхойлох. |
| Ямар зүйлгүйгээр энэ үр дүнг тайлбарлаж болох вэ? | Бүрэн restaurant CMS, зам оновчлох, loyalty campaign-ийн дэлгэрэнгүйгүйгээр customer урсгалын шаардлагыг бичиж болно. |
| Юуг одоо баталгаажуулах боломжгүй вэ? | Бодит payment/notification интеграц, үйлдвэрлэлийн ачаалал, хэрэглэгчийн ярилцлага, live courier map. Эдгээрийн төлөвийг таамаглал эсвэл хойшлуулсан ажил гэж тэмдэглэнэ. |
| Хэт дэлгэрүүлсэн баримтын зардал юу вэ? | Хэрэгжүүлээгүй дэд системийн тайлбар нь үндсэн шаардлагатай зөрчилдөх, шинэчлэлт хоцрох эрсдэл нэмнэ. |
| Дараа шинэ шаардлага ирвэл яах вэ? | Одоогийн ID, хамрах хүрээ, API/архитектур, тест, нотолгоонд үзүүлэх нөлөөг хамт шинэчилнэ. |

**“Just enough” шийдвэр:** SRS-д системийн ажиглагдах ажиллагаа, хэмжиж болох чанар, хязгаар, интерфейсийг бичнэ. Сонгосон framework, cache, database зэрэг хэрэгжүүлэх шийдлийн үндэслэлийг [архитектурт](../architecture/index.md) байрлуулна.

Албан ёсны бүртгэлүүд: [IEEE 830-1998](https://standards.ieee.org/ieee/830/1222/), [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html). Энэ багц нь стандартаар баталгаажсан conformity assessment биш.

## 3. Шалгаж болох таван шаардлага — US-2.2

Доорх таван ID-г хэрэглэгчийн `Week_02_FoodFlow.docx` болон дараагийн `Week_03_FoodFlow.docx`-ийн утгаар хадгалсан. Одоогийн үндсэн эх нь [SRS](../requirements/srs.md); энэ хэсэг W02-д шаардлага хэрхэн бичсэнийг тайлбарлана. Эхний тайлангийн зарим test-ийг хэмжүүр, давтан хүсэлт, шалгалтын хязгаар нь тодорхой байхаар найруулав.

**Эрэмбэ:** Эдгээр таван жишээ бүгд `MUST` буюу эхний суурь хувилбарт зайлшгүй. Шаардлагын өгүүлбэрт “should” зэрэг заавал биелэх эсэх нь бүдэг үг ашиглаагүй. `Owner` нь санал болгосон хянан батлах **үүрэг**, бодит хүний нэр эсвэл ярилцлага хийсэн тухай мэдэгдэл биш. `Verification` нь хийх шалгалтын арга; амжилттай гүйцэтгэсэн үр дүнг тусдаа нотолгоогоор бүртгэнэ.

### FR-01 — Хоолны жагсаалт

**Шаардлага:** Систем Menu-д идэвхтэй хоол бүрийн нэр, үнэ, зураг, товч тайлбарыг харуулна. **Төрөл / эрэмбэ:** FR / MUST. **Owner:** Product owner. **Эх сурвалж:** FoodFlow-ийн Menu урсгал, Анугийн эхний интеграцийн хэрэгцээ; бодит interview record байхгүй.

| Шалгах хэсэг | Тодорхойлолт |
| --- | --- |
| Given | ID нь ялгаатай 10 active, 2 inactive хоол; required талбарууд бүрэн test fixture. |
| When | Menu жагсаалтыг шинэ сессэд нээнэ. |
| Then | Active 10 хоол бүгд харагдаж, inactive 2 хоол харагдахгүй; харагдсан хоол бүрийн дөрвөн талбар fixture-тэй таарна. |
| Pass / fail | 10/10 active, 0/2 inactive; нэг ч хоол эсвэл required талбар зөрвөл fail. |
| Verification | `Test` — каталогийн fixture-тай UI/API integration test; `Inspection` — нэр, үнэ, зураг, тайлбарын харагдах байдлыг шалгах. |
| Нотолгоо | `TC-FR01` procedure; гүйцэтгэлийн log, screenshot, commit хүлээгдэж байна. |

### FR-04 — Сагсанд нэмэх

**Шаардлага:** Хоосон сагсанд сонгосон хоолыг нэг удаа нэмэхэд тухайн `food_id`-тай нэг мөр `quantity=1`-ээр үүснэ. **Төрөл / эрэмбэ:** FR / MUST. **Owner:** Frontend owner. **Эх сурвалж:** Анугийн UI/API integration хэрэгцээ; `P-ANU-02`-ын өгөгдлийн гэрээ тодорхой байх шаардлагатай холбоотой. Бодит persona interview байхгүй.

| Шалгах хэсэг | Тодорхойлолт |
| --- | --- |
| Given | Хоосон cart; `food_id=7` идэвхтэй хоол. |
| When | “Add to Cart” үйлдлийг нэг удаа хийнэ. |
| Then | Cart-д `food_id=7`, `quantity=1` бүхий нэг мөр бий болж, хоосон сагсны badge 0-оос 1 болно. |
| Pass / fail | Зөв ID-тай яг нэг мөр, quantity=1; бусад тохиолдол fail. |
| Verification | `Test` — UI үйлдэл болон cart response-ийг fixture-тэй тулгах. |
| Нотолгоо | `TC-FR04` procedure; test execution хүлээгдэж байна. |

Энэ жишээ нь хоосон сагсны нэг нэмэлтийг шалгана. Өмнө байсан хоолыг дахин нэмэх, quantity-ийн дээд хязгаар зэрэг хамаарах дүрмийг бүрэн SRS-д тусад нь шалгах ёстой.

### FR-11 — Нэг захиалга үүсгэх

**Шаардлага:** Зөв checkout өгөгдлөөр захиалга үүсгэхэд систем нэг `order_id` хадгалж буцаана; ижил хэрэглэгч ижил idempotency key, ижил өгөгдөлтэй хүсэлтийг давтахад шинэ захиалга үүсгэхгүй. **Төрөл / эрэмбэ:** FR / MUST. **Owner:** Backend owner. **Эх сурвалж:** Checkout user story, давхар захиалгаас сэргийлэх загварын хэрэгцээ; бодит owner interview байхгүй.

| Шалгах хэсэг | Тодорхойлолт |
| --- | --- |
| Given | Зөв сагс, хаяг, төлбөрийн арга; нэг user, шинэ key; эхний order count=0. |
| When | HTTP гэрээний дагуу захиалга үүсгэх ижил хүсэлтийг дараалан хоёр удаа илгээнэ. |
| Then | Эхний амжилттай үүсгэлт HTTP 201 ба order ID өгнө; давтан хүсэлт ижил order ID өгч, хадгалсан order count=1 байна. |
| Pass / fail | Хоёр хариуны ID ижил, хадгалсан захиалга 1; ID эсвэл count зөрвөл fail. Давтан хариуны status code-ийг тухайн OpenAPI гэрээтэй тулгана. |
| Verification | `Test` — request/response болон захиалгын хадгалалтыг хамтад нь шалгах integration test. |
| Нотолгоо | `TC-FR11` procedure; бодит HTTP integration test гүйцэтгэсэн гэж тэмдэглээгүй. |

Энэ procedure нь дараалсан давталтыг шалгана. Зэрэгцээ хүсэлт, key өөрчлөгдсөн payload, key-ийн хүчинтэй хугацаа, provider-ийн төлбөрийг давтан боловсруулах эрсдэлд тусдаа шалгалт хэрэгтэй. W06-ийн in-memory Python жишээний unit test нь үйлдвэрлэлийн түвшний distributed idempotency-ийн баталгаа болохгүй.

### NFR-01 — Menu-ийн харагдах үндсэн агуулгын хугацаа

**Шаардлага:** Баталсан mobile lab орчинд Menu хуудсыг 30 удаа хэмжихэд Largest Contentful Paint (**LCP**)-ийн p75 нь 2.5 секундээс ихгүй байна. **Төрөл / эрэмбэ:** NFR / MUST. **Owner:** QA. **Эх сурвалж:** Хэрэглэгчийн хурдан эхлэх хэрэгцээ, [web.dev-ийн LCP тайлбар](https://web.dev/articles/lcp). 30 lab run нь FoodFlow-ийн санал болгосон шалгах арга; эх сурвалжид бүх төсөл заавал 30 run хийхийг шаардсан гэсэн утга биш.

| Шалгах хэсэг | Тодорхойлолт |
| --- | --- |
| Given | Deploy URL, commit, browser/version, viewport, CPU/network profile, fixture, cache-ийн нөхцөлийг test protocol-д тогтоосон байна. |
| When | Нэг ижил protocol-оор 30 тусдаа navigation-ийн LCP-г секундээр хэмжинэ. |
| Then | Өсөхөөр эрэмбэлсэн 30 утгын nearest-rank p75 буюу 23 дахь утга ≤2.5 секунд байна. |
| Pass / fail | 30 хүчинтэй хэмжилт, орчны бүрэн бүртгэл, p75≤2.5 s; хэмжилт дутуу эсвэл орчин тогтоогоогүй бол гүйцэтгэл баталгаажаагүй. |
| Verification | `Analysis` — өгөгдөл, percentile тооцоог хянах; `Test` — browser performance хэмжилт. |
| Нотолгоо | `TC-NFR01` protocol ба raw results шаардлагатай; UI болон хэмжилтийн орчин бэлэн болсон гэж мэдүүлээгүй. |

LCP нь хуудасны үндсэн агуулга харагдах хугацаа; HTTP API-ийн p95 latency-тэй өөр хэмжүүр. 30 lab run-ийн acceptance check нь бодит хэрэглэгчийн field data-г орлохгүй. Анхны тайлангийн Akamai судалгааг энэ босгоны шууд эх гэж ашиглаагүй; 2.5 секундын тайлбарын үндэслэлд дээрх primary эхийг авсан.

### NFR-03 — Захиалгын эзэмшлийн хамгаалалт

**Шаардлага:** Нэвтэрсэн хэрэглэгч зөвхөн өөрийн захиалгын мэдээллийг уншина; өөр хэрэглэгчийн захиалгын ID-тай хүсэлтэд захиалгын мэдээлэл задрахгүй. **Төрөл / эрэмбэ:** NFR / MUST. **Owner:** Backend owner. **Эх сурвалж:** FoodFlow-ийн order ownership дүрэм, Анугийн `P-ANU-01` auth хэрэгцээ; Номин persona-ийн support хэрэгцээ нь баталгаажуулах таамаг хэвээр.

| Шалгах хэсэг | Тодорхойлолт |
| --- | --- |
| Given | A, B хоёр хэрэглэгч; B-ийн эзэмшдэг 100 захиалга; A-ийн баталгаажсан session. |
| When | A нь B-ийн 100 order ID бүрээр унших хүсэлт илгээнэ. Мөн A өөрийн нэг order-ийг унших control хүсэлт илгээнэ. |
| Then | B-ийн захиалгын мэдээлэл нэг ч удаа буцахгүй; control хүсэлт A-ийн зөв өгөгдлийг буцаана. Эрхгүй response нь API гэрээнд заасан хэлбэртэй байна. |
| Pass / fail | Эрхгүй 100 хүсэлтээс задрал 0, control хүсэлт амжилттай; бусдын өгөгдөл буцвал fail. |
| Verification | `Test` — authorization integration/security test; `Inspection` — response-д захиалгын мэдрэмтгий талбар ороогүйг тулгах. |
| Нотолгоо | `TC-NFR03` procedure; бодит HTTP auth/security execution хүлээгдэж байна. |

100 хүсэлт нь энэ тестийн түүврийн хэмжээ; системд аюулгүй байдлын бүх алдаа байхгүй гэсэн математик баталгаа биш. Python модульд `user_id` тулгасан нь token шалгах бодит authentication-ийг дангаараа хэрэгжүүлэхгүй.

## 4. Чанарын найман шалгах өнцөг

Анхны тайлангийн Correct, Unambiguous, Complete, Consistent, Ranked, Verifiable, Modifiable, Traceable гэсэн жагсаалтыг энэ сургалтын **SRS чанарын шалгах хуудас** болгон хэрэглэв. Үүнийг ISO/IEC/IEEE 29148-ийн шаардлага бүрийн яг найман шинжийн үгчилсэн жагсаалт гэж нэрлээгүй: баримтын чанар, нэг шаардлагын чанар, процессын заалтыг хооронд нь ялгах шаардлагатай. Нийцлийн албан дүгнэлт гаргаагүй.

| Шалгах өнцөг | FoodFlow-д тавих асуулт | Энэ шинэчлэлд хийсэн засвар |
| --- | --- | --- |
| Correct — хэрэгцээнд нийцсэн | Энэ нь хэрэглэгчийн ямар хэрэгцээг шийдэж байна вэ? | Эх сурвалж болон persona-ийн таамгийг ил тод тэмдэглэсэн. |
| Unambiguous — хоёрдмол утгагүй | “Хурдан”, “ердийн”, “автоматаар” зэрэг тайлбаргүй үг бий юу? | LCP босго, нэг order, эзэмшлийн дүрмийг тодорхойлсон. |
| Complete — бүрэн | Оролт, үйлдэл, үр дүн, boundary, алдааг тодорхойлсон уу? | Given/When/Then ба хязгаар нэмсэн; бүх edge case хаагдсан гэж мэдүүлээгүй. |
| Consistent — зөрчилгүй | Нэг ID өөр баримтад өөр утгатай болсон уу? | W02-ийн ID-г шинэ W03 DOCX-тэй тулгаж, одоогийн SRS рүү холбосон. |
| Ranked — ач холбогдол нь тодорхой | Зайлшгүй болон хойшлуулах зүйл ялгаатай юу? | Таван жишээнд MUST; scope-д хассан, хойшлуулсныг тусад нь бичсэн. |
| Verifiable — шалгаж болох | Pass/fail-ийг ямар ажиглалтаар шийдэх вэ? | Fixture, тоон босго, count, ID, control хүсэлт нэмсэн. |
| Modifiable — өөрчилж болох | Нэг өөрчлөлт хийхэд олон хуулбарыг гараар засах уу? | Одоогийн үндсэн эхийг SRS/traceability-д төвлөрүүлж, семинарын жишээг түүхэн тайлбар болгосон. |
| Traceable — мөрдөж болох | Эх сурвалжаас шаардлага, шалгалт руу очих уу? | Дараах найман багана, persona ID, procedure ID-аар холбоос үүсгэсэн. |

## 6. Peer review-д өгөх багц

Хянагчид өгөх агуулга: [Scope Charter](../requirements/scope.md), энэ баримтын SRS зураглал, таван шаардлага, найман баганатай хүснэгт. Дараах нь илгээхэд бэлэн **ноорог** бөгөөд бодит багт зурвас илгээсэн гэсэн нотолгоо биш.

> FoodFlow-ийн W02 хүрээ, SRS зураглал, таван шаардлага, мөрдөх хүснэгтийг хянаж өгнө үү. Хассан боломжийн үндэслэл ойлгомжтой эсэх, FR-11-ийн эхний ба давтан хүсэлтийн хил, NFR-01-ийн хэмжилтийн орчин, NFR-03-ийн control хүсэлт, persona-тай холбосон эх сурвалжийг шалгана уу. Санал бүрд нөлөөлөх хэсэг, шалтгаан, засах хувилбарыг тэмдэглэнэ үү.

| Хянагчийн шалгах зүйл | Бүртгэх нотолгоо |
| --- | --- |
| Scope-ийн оруулсан ба хассан зүйл хоорондоо зөрчилгүй юу? | Comment/issue URL, санал, шийдвэр |
| Шаардлага бүр нэг утга, тодорхой эрэмбэ, шалгах босготой юу? | Хамаарах ID, before/after diff |
| Persona-ийн асуудал үнэхээр тухайн шаардлагад хүргэж байна уу? | Эх сурвалжийн тайлбар; interview-ийн хэрэгцээ |
| Шалгалтын procedure ажиллуулахаар хангалттай юу? | Орчин, fixture, арга, дутсан нөхцөл |
| Саналыг шийдсэн үү? | Commit/PR, хянагчийн дахин шалгасан тэмдэглэл |

## 8. Эргэцүүлэл ба W03-д шилжүүлэх нь

**Bhatti-гаас хэрэглэх зүйл:** Handout-ийн Ch. 2, pp. 23–44; Ch. 4, pp. 67–81 гэсэн чиглэл нь уншигчид хэрэгтэй хүрээг сонгох, шаардлагыг ойлгомжтой бичихэд тусалсан. “Зөвхөн өөрийн захиалгыг уншина” гэж бичээд зогсохын оронд хэн, ямар ID, ямар хариу авч болохыг шалгах procedure нэмэв.

**Chinchilla-гаас цааш хэрэглэх зүйл:** Ch. 5, pp. 53–55-ийн scoping чиглэлийг “одоо юу баталж болох вэ?” гэсэн асуултаар хэрэглэв. Төлөвлөсөн веб бүтээгдэхүүн, OpenAPI гэрээ, ажиллуулж болох Python жишээг тус тусын нотолгоотой хадгална.

**Онол ба одоогийн ажлын зөрүү:** Owner/interview болон peer review шаардлагатай ч одоогийн хавсралтад тэдгээрийн бодит үр дүн байхгүй. Иймээс зохиомол дүр, санал болгосон үүрэг, гүйцэтгээгүй test procedure-ийг баталгаажсан үр дүнтэй адил тэмдэглэхээс зайлсхийв.

| Standup / retrospective асуулт | Энэ шинэчлэлийн хариу |
| --- | --- |
| Ямар IEEE хэсгийг зурагласан бэ? | Зорилго, scope, overall description, interfaces, FR/NFR, constraints, appendix. |
| Traceability-д хэдэн шаардлага байна вэ? | W02 жишээнд 5; бүгд 8 баганатай. |
| Ямар persona холбоо нэмсэн бэ? | FR-04 → `P-ANU-02`; NFR-03 → `P-ANU-01`. |
| Юу сайн болсон бэ? | Шаардлага ба хэрэгжүүлэх шийдэл, procedure ба test result-ийг ялгасан. |
| Юу тодорхойгүй байсан бэ? | LCP хэмжих орчин, давтан хүсэлтийн код, owner-ийн баталгаа. |
| Дараа юу өөрчлөх вэ? | W03-ийн бүрэн багцад хамаарал, edge case, owner, interview/peer review-ийн бодит нотолгоог нэмнэ. |

Энэ нь шинэчлэлийн өөрийн үнэлгээ; бодит standup эсвэл retrospective уулзалт хийсэн тухай тэмдэглэл биш. SRS нь систем **юу хийхийг**, [архитектур](../architecture/index.md) нь түүнийг **яагаад, ямар хэсгүүдээр хэрэгжүүлэхийг** тайлбарлана. “Давтан хүсэлт шинэ захиалга үүсгэхгүй” гэдэг нь шаардлага; түүнийг Redis, database constraint эсвэл өөр механизмаар хэрэгжүүлэх нь тусдаа шийдвэр юм.
