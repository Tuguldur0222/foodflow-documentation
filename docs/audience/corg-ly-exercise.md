# UE-1 — Corg.ly Pet Translation API roleplay

**Зорилго:** Charlotte үйлчилгээ нэвтрүүлэхээр бэлтгэж буй нөхцөлд persona, Curse of Knowledge, Writer-in-the-Middle ойлголтыг хэрэглэх. **Эх:** `Software_Project_Documentation_Week_01_Handout.pdf`, p. 2 — [эх сурвалжийн бүртгэл](../../sources/README.md). **Төлөв:** нэг Markdown баримт бүхий сургалтын дасгал.

Доорх persona, API зам, талбар, README өгүүлбэрүүдийг дасгалд зориулан зохиосон. Номын Corg.ly README-ээс шууд эшилсэн өгүүлбэр эсвэл бодит үйлчилгээний баталгаажсан гэрээ биш. Charlotte-ийн нэр, Pet Translation API-ийн launch гэсэн нөхцөлийг handout-аас авсан; техникийн нарийн утгыг зохиомол жишээ гэж ялгав.

## A. Developer persona

| Талбар | Утга |
| --- | --- |
| Нэр | Маяа — зохиомол persona |
| Компани | PawTech Studio — зохиомол компани |
| Үүрэг | Mobile developer |
| Өдөр тутмын хэрэгсэл | Flutter, Dart, VS Code, Postman, GitHub Actions |
| Зорилго | Pet Translation API-ийн нэг амжилттай хүсэлтийг туршилтын апптай холбох |
| Хэрэгцээ | API key авах дараалал, оролтын төрөл, үр дүнгийн талбар, дэмжих хувилбар, алдааны заавар |
| Гурван таамагласан саад | Token хаанаас авах нь тодорхойгүй; payload-ийн жишээ дутуу; дахин оролдох нөхцөл тодорхойгүй |
| End-end user | Маяагийн аппын хэрэглэгч; амьтны дууны тайлбарыг ойлгомжтой харахыг хүснэ |

Зохиомол хэллэг: “Эхлээд нэг хүсэлт ажиллахыг хармаар байна. Key, оролтын жишээ, алдааны тайлбарыг тус тусад нь хайхгүй бол хурдан туршина.” Бодит ярилцлага хийгдээгүй; дээрх саадыг Маяатай төстэй хөгжүүлэгчээр баталгаажуулах шаардлагатай.

## B. Гурван өгүүлбэрийн before/after

| Өмнө — зохиомол ноорог | Нуугдсан мэдлэг | Дараа — ойлгомжтой болгох жишээ |
| --- | --- | --- |
| “Translate endpoint-д ердийн payload илгээ.” | Method, зам, оролтын төрөл, үр дүнгийн талбар алга. | “Орчуулгын жишээг туршихын тулд `POST /v1/translate` хүсэлтэд `text`, `sourceLanguage`, `targetLanguage` бүхий JSON илгээнэ. Амжилттай үед `translation` талбарыг уншина.” |
| “Default auth ашигла.” | Key авах дараалал, header-ийн хэлбэр тодорхойгүй. | “Жишээ орчны dashboard-аас API key аваад хүсэлтдээ `Authorization: Bearer <api_key>` header нэмнэ. Жинхэнэ key-г код эсвэл public repository-д хадгалахгүй.” |
| “Transient алдаанд хэвийн retry хий.” | Аль алдаа, ямар хугацаа, ямар хязгаартайг хэлээгүй. | “Дахин оролдох боломжтой хариунд үйлчилгээний баталсан retry бодлогыг дагана. HTTP 429-ийн жишээнд серверийн өгсөн хүлээх хугацааг тайлбарлаж, оролтын 4xx алдааг эхлээд засахыг заана.” |

Эхний шинэчилсэн өгүүлбэр уншигчийн авах үр дүнг эхэнд тавьсан. Дээрх URL, талбар, token хэлбэр нь тайлбарын жишээ бөгөөд Charlotte API эзнээр батлуулсны дараа л бодит гэрээнд оруулж болно. Тодорхой найруулга нь техникийн үнэн зөв байдлын баталгаа болохгүй.

```diff
- Translate endpoint-д ердийн payload илгээ.
+ Орчуулгын жишээг туршихын тулд POST /v1/translate хүсэлтэд
+ text, sourceLanguage, targetLanguage бүхий JSON илгээнэ.
+ Амжилттай үед translation талбарыг уншина.
```

## C. Charlotte-ийн Writer-in-the-Middle эргэцүүлэл

Launch-ийн өмнө Charlotte маркетингийн амлалтыг API-ийн бодит хүрээтэй тулгаж, хөгжүүлэгчийн хэрэгцээг багуудад ойлгуулна. Engineering багаас оролтын төрөл, key-ийн эрх, дэмжих хэл, алдааны хариуг батлуулна. Product багаас ямар боломж эхний хувилбарт орохыг тодруулж, sales-д баталгаагүй боломж амлуулахгүй тайлбар өгнө. DevRel-д нэг хүсэлтийг эхнээс нь турших заавар, support-д нэвтрэлт ба retry-ийн асуудлыг ялгах мэдээлэл бэлтгэнэ.

Маяа баримтын шууд уншигч боловч түүний аппын хэрэглэгч нь үр дүнг эцэст нь харна. Иймээс Charlotte зөвхөн API нэршлийг гоё тайлбарлах бус, буруу ойлголт бүтээгдэхүүнд яаж нөлөөлөхийг асууна. Тодорхойгүй retry бодлогыг өөрөө зохиож үнэн мэт нийтлэхгүй; эзэн, шийдэх хугацаа, баталгаажуулах аргыг тэмдэглэнэ. Machine readers-д өгөх schema болон хүний унших жишээ ижил гэрээтэй байхыг хянана.
