Төрөл тус бүрийн хоёр өгүүлбэр. Getting Started-д “эхлэхийн тулд юу хийх вэ?” гэж асуудаг бөгөөд зам нь first-steps/, intro/install/, absolute_beginners/ зэрэг байдаг. Эхний жижиг үр дүнг хурдан харуулна.
Tutorial-д “энэ ажлыг яаж дуусгах вэ?” гэж асуудаг бөгөөд tutorial/, intro/tutorial01/, user/quickstart зэрэг дараалсан хичээлд ордог. Уншигч өмнөх алхмын үр дүнг дараагийн алхамд хэрэглэнэ.
Reference-д “тодорхой нэр, тохиргоо юу гэсэн үг вэ?” гэж асуудаг бөгөөд reference/, ref/models/, reference/arrays дотроос хайна. Энэ төрлийг эхнээс нь дуустал уншихаас илүү хэрэгтэй хэсэгт нь очиход ашиглана.
API Docs-д “ямар параметр оруулах, юу буцах вэ?” гэж асуудаг бөгөөд FastAPI-ийн /docs, Django-ийн ref/models/querysets/, NumPy-ийн reference/generated/numpy.array.html зэрэг байршилтай. FoodFlow-д энэ нь GET /menu болон POST /orders-ийн request, response, алдааны код болно.
2 FoodFlow-ийн уншигчийн persona
Анхдагч persona: Ану, зохиомол Nomad Eats компанийн junior frontend developer. Тэр VS Code, React, TypeScript, Chrome DevTools, Postman, GitHub хэрэглэдэг. Menu → Cart → Checkout урсгалыг API-тай холбох үед auth, алдаа, version-ийг нэг дороос мэдэх шаардлагатай. Саруул гэдэг хоол захиалагч нь end-end user: Анугийн API баримт ойлгосон эсэх нь эцсийн хэрэглэгчийн дэлгэцэд нөлөөлдөг.
Доорх гурван асуудлын хэв маягийг олон нийтийн бодит хэлэлцүүлгээс авсан. Асуулт тавьсан хүмүүсийг Ану гэж нэрлээгүй; persona нь зохиомол.

Дэмжих persona: Билэгт backend хөгжүүлэгч давхар захиалга, өгөгдлийн сангийн хил тодорхой байхыг хүснэ. Номин support ажилтан төлөв болон алдааны дараагийн алхмыг хурдан олохыг хүснэ. W04-ийн шийдвэрүүд эдгээр асуудалтай холбогдоно.

Гурав дахь засварт хэрэглэгчид чухал үр дүн болох “давхар захиалга үүсгэхгүй”-г эхэнд тавьж, дараа нь key-г тайлбарласан. Инженер бус уншигчаас “дараа нь дэлгэцэд юу харагдах вэ?”, “token-ийг хаанаас авах вэ?”, “захиалга давхардахгүйг яаж мэдэх вэ?” гэж асууж, бодит хариултыг review-д тэмдэглэх ёстой.
4 Writer in the Middle багт өгөх үнэ цэнэ
FoodFlow багийн баримт бичиг бичигч нь marketing, product, sales, support, DevRel, engineering, machine readers-ийн хооронд нэг ойлголт дамжуулах хүн байна. Marketing-д “idempotent API”-г “давхар захиалга үүсэхээс сэргийлнэ” гэж тайлбарлана. Product-д захиалгыг цуцлах хүсэлт аль төлөв хүртэл үйлчлэхийг FR-13-тай холбоно. Sales-д QPay, карт, бэлэн мөнгөний сонголтыг батлагдаагүй үйлчилгээ мэт хэт амлахгүй. Support-д 409 алдаа гарвал хэрэглэгчид дараа нь юу хийхийг хэлэх заавар өгнө. DevRel-д token авах, Menu унших, Order үүсгэх жишээг нэг дарааллаар бэлдэнэ. Engineering-д FR-11, test, C4, ADR-003 хооронд холбоос үүсгэнэ. Machine readers-д OpenAPI schema болон тогтмол code, message талбар машинд уншигдах гэрээ болно.
Энэ долоон ажил нь файл бичихээс илүү утгатай. Бичигч backend багийн бодит боломжийг асууж, frontend багийн хэрэглэх үгийг тохируулж, support-ийн мэдэх ёстой алдааг нэг загварт оруулна. Саруул хоолоо захиалж буй эцсийн хүн боловч Ану API-г буруу ойлговол Саруулын дэлгэцэд төлбөрийн алдаа буруу харагдана. End-end user гэдэг нь зөвхөн README уншигч биш, уншигчийн хийсэн бүтээгдэхүүнийг ашиглах хүн юм. Би нэгж бүрийн эзнээс баримтын утгыг баталгаажуулж, батлагдаагүй шийдвэрийг тодорхойгүй гэж тэмдэглэнэ. Ингэвэл дараа нь хэн нэгэн кодыг уншаад санааг таах шаардлага багасна.

UE-1 Corg.ly Pet Translation API
Энэ бол Charlotte-ийн дүрд орж хийсэн сургалтын ажил. Corg.ly API болон доорх README өгүүлбэрүүд нь handout-ийн зохиомол жишээ; бодит үйлчилгээний гэрээ, бодит ярилцлагын тэмдэглэл биш.
A Developer persona
Маяа бол зохиомол PawTech Studio компанийн mobile developer. Flutter, Dart, Postman, GitHub Actions хэрэглэж, Pet Translation API-г нэг өдөрт туршилтын апптай холбох зорилготой. Түүнд token авах газар, request JSON-ийн хэлбэр, дэмжих хэл, rate limit, алдааны үед хийх алхам чухал. Маяагийн аппын эцсийн хэрэглэгч нохойн дууны тайлбарыг ойлгомжтой харахыг хүснэ.
Зохиосон хэллэг: “Request нэг удаа ажиллахыг харах хэрэгтэй. Token, хэлний код, алдааны жишээ гурвыг гурван өөр газраас хаймааргүй байна.”

C Writer in the Middle
Launch-ийн өмнө Charlotte маркетингийн амлалтыг API-ийн бодит хүрээтэй тулгана. API багаас хэлний код болон алдааны хариуг батлуулж, DevRel-д ажиллах request хүргэнэ. Support-д 429, 401, 5xx-г ялгах заавар өгнө. Маяа жишээг ойлгож ажиллуулбал түүний аппын эцсийн хэрэглэгчид зөв үр дүн харагдана.
“Retry хэвийн” гэдгийг итгэлтэй мэт бичихийн оронд бодлогыг инженерээс батлуулах, батлаагүйг ил тод тэмдэглэх нь бичигчийн хариуцлага. Ингэж Charlotte баг бүрийн хэлсэн зүйлийг нэг бодит, шалгаж болох баримтад холбож байна.
Эх сурвалж: Week 01 handout UE-1 (p. 2); Bhatti Ch. 1 pp. 1–3, 15–16; Chinchilla Ch. 1 p. 5 (хуудасны заалт handout-аас).
